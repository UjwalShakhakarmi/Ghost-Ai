## Architecture Decisions

- Created multi-file Prisma schema structure with `prisma/models/project.prisma` containing `Project` and `ProjectCollaborator` models.
- Configured cached PrismaClient singleton in `lib/prisma.ts` with conditional branching for `prisma+postgres://` (Accelerate) vs `@prisma/adapter-pg`.
- Added `lib/projects.ts` as the shared project data-access helper (owned/shared lookups, create/rename/delete) used by both API routes and server components.
- `GET/POST /api/projects` and `PATCH/DELETE /api/projects/[projectId]` enforce Clerk auth (401) and owner-only mutation checks (403) before touching Prisma.
- `/editor` and `/editor/[projectId]` are server components that fetch owned + shared projects directly via `lib/projects.ts` (no client-side fetch for initial load); `[projectId]` marks the active workspace so delete can redirect correctly.
- Replaced the mock `useProjectDialogs` hook with `useProjectActions` (`hooks/use-project-actions.ts`), which calls the real REST API and uses `router.push`/`router.refresh` instead of local mock state.
- The create dialog's room ID preview (slugified name + client-generated short suffix) is cosmetic only; the authoritative project ID is always the Prisma-generated `cuid` returned by `POST /api/projects`, which is then reused as the workspace route segment (future Liveblocks room id) — the two are never allowed to diverge.
- Sidebar project rows now show a formatted `updatedAt` date instead of a `slug`, since `Project` has no slug field in the schema.
- Added `lib/project-access.ts` outside the page component: `getCurrentIdentity()` (Clerk `userId` + primary email) and `hasProjectAccess(project, identity)` (true for the owner, or for a collaborator matched by email against `ProjectCollaborator`).
- Renamed the workspace route segment from `/editor/[projectId]` to `/editor/[roomId]` to make explicit that the route segment, the Prisma `cuid`, and the future Liveblocks room id are the same canonical value.
- `/editor/[roomId]` is a server component: redirects unauthenticated visitors to `/sign-in`, and renders the new `components/editor/access-denied.tsx` (centered, lock icon, link back to `/editor`) for missing or unauthorized projects, before ever rendering the workspace shell.
- Split the "active project" workspace UI out of `EditorWorkspace` (now home-listing only) into a dedicated `components/editor/editor-workspace-shell.tsx`, since the two views diverged too much to share one component: full-viewport layout, `EditorNavbar` showing the project name plus new Share/AI-toggle actions, `ProjectSidebar` with the current room highlighted (`activeProjectId` prop), a canvas placeholder, and a new `components/editor/ai-sidebar.tsx` slide-over placeholder on the right.
- AI sidebar toggle remains UI-only per spec scope — no AI chat logic wired yet.
- Added `lib/collaborators.ts`: `listCollaboratorsWithClerkData()` reads `ProjectCollaborator` rows and enriches them via Clerk's Backend API (`clerkClient().users.getUserList({ emailAddress })`), matched back to each collaborator by lowercased email; falls back to email-only display when no Clerk user is found. `addCollaborator`/`removeCollaborator` upsert/delete by the `projectId_email` compound key. No local user table was added, per spec.
- `GET/POST/DELETE /api/projects/[projectId]/collaborators` (single route file): GET is available to the owner or any collaborator (`hasProjectAccess`); POST and DELETE are owner-only (403 otherwise), matching "collaborators can view only, not invite/remove/manage."
- The Share button in `EditorNavbar` now opens `components/editor/share-dialog.tsx` (wired via `hooks/use-share-dialog.ts`) instead of a no-op. The dialog always shows the project link (with `Copied!` feedback on copy) and the collaborator list; the invite form and per-row remove buttons only render when `project.isOwner` is true. `isOwner` is computed server-side in `app/editor/[roomId]/page.tsx` (`project.ownerId === identity.userId`) and passed down through `EditorWorkspaceShell`.
- Collaborator avatars use `next/image` with `unoptimized` (Clerk-hosted URLs aren't in the Image Optimization allowlist) and fall back to an initial-letter badge when no Clerk user/avatar is found.
- `liveblocks.config.ts` (root) types `Presence` as `{ cursor: {x,y} | null; isThinking: boolean }` and `UserMeta.info` as `{ name, avatar, color }`, per spec. Other Liveblocks type slots (Storage/RoomEvent/ThreadMetadata/RoomInfo) are left as `Record<string, never>` placeholders until Canvas Core needs them.
- Added `lib/liveblocks.ts`: a cached `Liveblocks` (server SDK) client via `getLiveblocksClient()`, plus `getCursorColorForUser(userId)` — a deterministic string-hash into a fixed 14-color palette, so the same user always gets the same cursor color. The client is constructed lazily (inside the getter, not at module load) because the SDK validates the secret key format eagerly in its constructor, which would otherwise crash `next build`'s page-data-collection step whenever the key is a placeholder.
- `POST /api/liveblocks-auth` requires Clerk auth (401), reads `{ room }` from the body (the room ID is the project's Prisma `cuid`, matching the "project ID and Liveblocks room ID are the same value" decision from spec 07/08), verifies access via `hasProjectAccess` (403 otherwise), calls `getOrCreateRoom` (private by default, `usersAccesses` granting the caller `room:write`) and then `updateRoom` to patch the same grant onto an already-existing room — this second call is what lets a second collaborator (not the room's original creator) actually get in, since `getOrCreateRoom` only applies its permissions when it creates the room. Returns the `identifyUser` session body/status directly (ID-token auth), with `name`/`avatar`/`color` attached as `userInfo`.
- `getCurrentIdentity()` in `lib/project-access.ts` was extended with `name` and `avatarUrl` (derived from the same `currentUser()` call already being made for `email`) since the Liveblocks auth route needed them and it's still just "current Clerk identity" data — no new Clerk API call, backward compatible with existing callers.
- Installed `@liveblocks/node` (the other `@liveblocks/*` packages and `@xyflow/react` were already present). No client-side `LiveblocksProvider`/`RoomProvider` wiring yet — spec 10 is backend-infrastructure only; the workspace shell doesn't call `/api/liveblocks-auth` yet.
- Added `types/canvas.ts`: `CanvasNode = Node<CanvasNodeData, "canvasNode">` and `CanvasEdge = Edge<Record<string, unknown>, "canvasEdge">` (typed for `@liveblocks/react-flow`'s `useLiveblocksFlow<N, E>`), plus `CanvasNodeData` (`label`, `color`, `shape`). Also added `NODE_SHAPES` and `NODE_COLORS`/`DEFAULT_NODE_COLOR` here as plain data (no rendering component yet) since `ui-context.md` already documents this exact palette/shape set as living in `types/canvas.ts` — this spec is the first one to create the file, so it made sense to seed it now rather than leave a gap for the next spec to discover.
- `components/editor/canvas.tsx` is the Liveblocks room wrapper: `LiveblocksProvider` (`authEndpoint="/api/liveblocks-auth"`) → `RoomProvider` (`id={roomId}`, `initialPresence={{ cursor: null, isThinking: false }}`) → `ErrorBoundary` (from `react-error-boundary`, newly installed) → `ClientSideSuspense`, wrapping the new `components/editor/canvas-flow.tsx`, which calls `useLiveblocksFlow({ suspense: true, nodes: { initial: [] }, edges: { initial: [] } })` and renders `<ReactFlow>` with `connectionMode={ConnectionMode.Loose}`, `fitView`, a dotted `<Background>`, and `<MiniMap>`. `colorMode="dark"` was added since the app is dark-only per `ui-context.md` and React Flow defaults to light styling.
- `EditorWorkspaceShell`'s canvas placeholder `<main>` now renders `<Canvas roomId={project.id} />` directly (the room ID is always the project's `cuid`, consistent with the existing project-ID/room-ID alignment decision). No controls, custom node/edge components, persistence, or AI behavior were added, per this spec's explicit scope limits.
- `components/editor/canvas-flow.tsx` now wraps its content in `ReactFlowProvider`/`CanvasFlowInner` (was a single component) because creating nodes on drop needs `useReactFlow()`'s `screenToFlowPosition`, and that hook only works in a component that's a descendant of `ReactFlowProvider` — a component that itself renders the top-level `<ReactFlow>` doesn't count as being "inside" it. `onDragOver`/`onDrop` are passed straight through as native HTML props on `<ReactFlow>` (it extends `HTMLAttributes<HTMLDivElement>`), no extra wrapper div needed.
- Added `components/editor/shape-panel.tsx`: a `<Panel position="bottom-center">` (built-in React Flow overlay, not custom-positioned CSS) with one draggable icon button per shape (`RectangleHorizontal`/`Diamond`/`Circle`/`Pill`/`Cylinder`/`Hexagon` from lucide-react). Drag payload (shape + default width/height) is serialized as JSON on a custom `application/x-canvas-shape` DataTransfer type — sensible defaults: rectangle 160×80 (wider than tall), circle 120×120 (square), diamond 170×170 (deliberately larger so the inscribed-diamond usable area still fits a label), pill 170×70, cylinder 130×130, hexagon 150×120.
- On drop, `canvas-flow.tsx` reads that payload, converts the pointer position to canvas coordinates via `screenToFlowPosition`, and adds the node the same way React Flow's own controlled pattern does: `onNodesChange([{ type: "add", item: newNode }])` — confirmed by reading `@liveblocks/react-flow`'s source that its `onNodesChange` mutation explicitly handles the `"add"` change type (there's no separate `addNode`/`setNodes` escape hatch exposed by `useLiveblocksFlow`). New nodes get `type: "canvasNode"`, empty `label`, `color: DEFAULT_NODE_COLOR.fill`, and `shape` from the payload.
- Node IDs are `${shape}-${Date.now()}-${counter}` per spec, with a module-level counter to guarantee uniqueness even for drops in the same millisecond.
- Added `components/editor/canvas-node.tsx`, registered as `nodeTypes={{ canvasNode: CanvasNodeRenderer }}` on `<ReactFlow>`. Per spec scope, every shape renders identically for now — a bordered rectangle with the label centered (no shape-specific SVGs yet) — but it does use the real fill/text color pairing from `NODE_COLORS` (falling back to `DEFAULT_NODE_COLOR` if `data.color` doesn't match a known pair) rather than hardcoding a color, so dropped nodes are already visually correct once shape-specific rendering lands later. Deliberately did not add connection `Handle`s in this pass — the spec's renderer description ("simple bordered rectangle with the label centered") doesn't mention them, and check-when-done doesn't test connecting to these nodes, so that's left for the spec that adds real shape rendering.
- **Root cause of the "canvas floats in a card/box" complaint**: React Flow's `colorMode="dark"` sets its own default background to `#141414` (`.react-flow.dark`'s `--xy-background-color-default`), which does not match the app's actual `--bg-base` token (`#080809`). Two visually-close-but-different darks sitting next to each other reads as a distinct rectangle even with zero border/shadow/radius on our own wrapper divs — confirmed by rendering both colors side-by-side in an isolated static repro (see session notes). Fixed by passing `bgColor="var(--bg-base)"` to `<Background>` and `style={{ backgroundColor: "var(--bg-base)" }}` to `<ReactFlow>` itself in `canvas-flow.tsx`, so both the visible dotted layer and the root pane now use the exact same token as the rest of the app.
- **Root cause of the "sidebar peeks/doesn't fully hide" complaint**: `shadow-2xl`'s blur radius extends beyond the sidebar's own border-box, and since `box-shadow` isn't clipped by the element's own `transform`, the shadow still bled a few pixels into the visible canvas area even when the sidebar was translated fully off-screen (measured empirically: a 1/255 RGB gradient in the shadow's blur zone, gone once the shadow is removed). Fixed in both `project-sidebar.tsx` and `ai-sidebar.tsx` by making `shadow-2xl` conditional on `isOpen` (applied alongside `translate-x-0`, absent when closed) instead of always-on — no shadow exists to bleed when there's nothing visible to cast it.
- Hardened `shape-panel.tsx`'s drag source from a native `<button draggable>` to a `<div role="button" tabIndex={0} draggable>`: form controls have historically inconsistent native HTML5 drag support across browsers (WebKit/Safari in particular), so a plain div is the more universally reliable drag source. The rest of the drag-and-drop pipeline (dataTransfer MIME payload, `onDragOver`/`onDrop` on `<ReactFlow>`, `screenToFlowPosition`, `onNodesChange([{ type: "add", ... }])`) was re-traced end-to-end and found correctly wired — confirmed via `@xyflow/react`'s actual bundled source that unrecognized props like `onDrop`/`onDragOver` passed to `<ReactFlow>` really do get spread onto its root DOM element (`...rest` in the source), so nothing was silently dropped there either.
